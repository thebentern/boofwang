# Baofeng UV-82 - notes

Offsets transcribed from CHIRP's `uv5r.py` (GPL-3.0). See [../provenance.md](../provenance.md).

The connect screen also offers this radio through a clip-on BLE-to-serial
dongle, untested - see [ble-dongle.md](ble-dongle.md).

## Verified write session, 2026-08-20

| | |
|---|---|
| Radio | Baofeng UV-82, firmware `N822413` |
| Ident | `aa 30 79 04 00 05 20 dd` |
| Adapter | FTDI FT232R, 9600 8N1 |
| Image | 6,472 bytes |
| Baseline sha256 | `7ba5ec72f394a8e4a8502cf225bdf27e0f7e45c4a85b579d8d767f01c4a76df0` |

The full cycle, verified at each step by reading the radio with a separate
Python implementation outside the app:

1. **Baseline.** Raw read, byte-identical to the committed fixture - the radio
   had not changed since it was first captured.
2. **Edit.** Channel 2 renamed `FRS 1` to `BOOF` in the app. The diff reported
   5 bytes in 1 block, 0 outside the ranges the driver owns.
3. **Write.** One 16-byte block sent, read back and compared.
4. **Independent check.** A raw read found **exactly 5 differing bytes out of
   6,472**, all of them in slot 2's name field at image `0x1018`-`0x101C`:
   `46 52 53 20 31` -> `42 4f 4f 46 ff`. Nothing else moved.
5. **Restore.** Renamed back and written again. The radio returned to
   `7ba5ec72...`, byte for byte.

Traffic for the whole restore was 45 bytes out and 238 in: handshake, one write
frame, one read-back. A one-channel edit costs one block, which is the point of
diffing against the image the radio was read from.

That session predates two changes on the wire. Verification now reads the
`0x40` window a written block falls in rather than the block alone - the UV-5R
notes say why - which would make the same restore 286 bytes in. And every
write since 2026-11-09 also reads four blocks after the handshake, 16 bytes out
and 276 in, which no session on any radio has sent yet. See
[which radio is on the cable](#which-radio-is-on-the-cable).

## Writing

Writes use `0x58` with a 16-byte payload, not the `0x40` blocks reads use, and
the address is the **radio** address - the image offset less the eight ident
bytes that prefix the image but do not exist on the radio. Confusing the two
writes every block one notch out, and reading back would not catch it because
the read is shifted the same way.

Only blocks that differ from the image the radio was read from are sent. A
restore supplies no base image, deliberately - it expects the radio to differ,
which is the point of restoring - so the driver reads the radio first and diffs
against that.

### What is never sent

CHIRP skips image `0x0CF8`-`0x0D08` and `0x0DF8`-`0x0E08` on every upload.
Nothing documents what lives there. Both fall outside the three ranges this
driver owns - channels at `0x0008`-`0x0808`, settings at `0x0E28`-`0x0E58` and
names at `0x1008`-`0x1808` - so a diff-driven write cannot reach them. On the
UV-5G bench unit the second window begins with the ASCII string `FANGXIAODONG`,
which is firmware data no channel encoder has any business touching. A test asserts that arithmetic rather than
trusting it, and the driver refuses outright if a changed block ever lands there.

### Receive-only

CHIRP's `_is_txinh` for this family (`uv5r.py`) recognizes exactly one marker:
`FF FF FF FF` in the transmit frequency. A transmit frequency of zero is **not**
an inhibit to it - it measures the distance from the receive frequency, calls
the channel a split, and reports transmit as enabled. An earlier version of this
section claimed CHIRP read the zero filling as inhibited too; that is true of
`baofeng_common.py`, which is the UV-5R Mini's family, and it looked right for
this one until it was checked against `uv5r.py` itself.

boofwang decodes both fillings as inhibited - reading a channel as less capable
than CHIRP would is the safe direction - and writes only the all-ones marker.
A record it changes for any reason is written with `FF FF FF FF`, which costs
nothing on the wire: a channel record is exactly one 16-byte write block, so a
record that already differs was being sent anyway. A record nothing changed in
is carried through byte for byte, zero filling included, which is what keeps
`encode(decode(image), image)` exact.

The residual: an image that already carries a zero filling shows those channels
as transmit-capable in CHIRP, whether or not boofwang was ever in the loop, and
boofwang leaves the ones you never edit as it found them. No hardware capture
has contained a zero filling yet - the marker was checked on the N822413 unit
and its fixture, which carry only `FF FF FF FF`.

### The UV-82HP is refused

It shares the plain UV-82's magic and this driver identifies it, but it has
three power levels where the plain radio has two, indexed by the same two-bit
field. This build models two, so a Low channel on an HP would decode as High and
be written back at 8 W - promoting a channel the user never touched. Reading and
backing one up is unaffected.

## Which radio is on the cable

This applies to the whole family - the UV-82, UV-5G and UV-5R share the driver.

`identHash` is the ident and the firmware string, and neither names a unit. Two
pairs of real radios show it: each pair below sends the same ident and reports
the same firmware, so `identHash` cannot tell them apart.

| Radio | Ident | Firmware | Span bytes that differ |
|---|---|---|---|
| UV-5G on the bench | `aa 44 46 04 00 04 70 dd` | `HN5RV011` | 34 of 160 |
| UV-5G in CHIRP's test images | the same | the same | |
| UV-5R on the bench | `aa 30 76 04 00 05 20 dd` | `HN5RV011` | 22 of 160 |
| UV-5G Pro in CHIRP's test images | the same | the same | |

What is committed of CHIRP's images is the part this table rests on - each
one's ident, firmware window and 160 span bytes - in
`test/fixtures/uv5r-family-chirp-units.json`, and
`test/lib/radios/uv82/unit-fingerprint.spec.ts` holds the table to it in every
run: the shared ident and firmware, the 34 and the 22, and that all seven
images below hash differently. The images themselves are GPL-3.0 and fetched
into `reference/` by `./scripts/fetch-reference.sh`; with them there, the spec
checks the excerpt against them too.

Until 2026-11-09 `unitFingerprint` returned null for this family, so a backup
was bound to the radio by `identHash` alone. A backup of one UV-5G was
accepted for writing another, and a restore diffed one unit's image against
whichever radio was on the cable and sent the difference.

**The fingerprint** is a sha256 over image `0x1848`-`0x18A8`, `0x18B8`-`0x18C8`
and `0x18D8`-`0x1908`, which are radio `0x1F00`-`0x1F60`, `0x1F70`-`0x1F80` and
`0x1F90`-`0x1FC0`. These are CHIRP's numbers, not ours. `_do_upload` in
`uv5r.py` takes `aux_i1` to `aux_i3` from exactly those image offsets and
compares them with what `_get_aux_data_from_radio` reads off the radio. It
uploads the aux block only when all three match, and on a radio with the
dropped-byte quirk a mismatch refuses the upload with "Upload back to same
radio". Its default aux ranges write the welcome message, the squelch
thresholds at `0x1F60` and `0x1F80` and the band limits at `0x1FC0`, none of
them inside a span. The squelch thresholds are the gaps between the spans, and
they are what CHIRP's service settings edit. The whole aux area goes only when
the spans already match, so CHIRP changes a fingerprinted byte only through
its range override, below.

What the spans hold is not documented. In the UV-5G pair the differences fall
within radio `0x1F00`-`0x1F0F`, `0x1F77`-`0x1F79`, `0x1F90`-`0x1F9F` and
`0x1FA8`-`0x1FA9`. In the UV-5R pair they fall only within
`0x1F02`-`0x1F18`; everything else in those two radios' spans is identical,
including long runs of `0x01` and `0x96` that look like defaults nobody
calibrated. All seven images compared - the three bench
captures and four CHIRP test images - hash differently. Two units that
calibrated identically would collide. So would a radio whose aux area CHIRP's
range override has overwritten with another unit's, since that upload sends
everything regardless. The DM-32UV's calibration hash has the same weakness,
over a whole 4 KiB page. Here the bytes that differed between units were a few
dozen values from a short list, and nothing yet says how often two radios from
one batch come out alike. On a collision the twin's backup or image would pass
the driver's check, as any backup with the same firmware did before the
fingerprint. The one place a collision refuses instead is the fleet run: its
check for the same radio presented twice, inert on this family until now, would
refuse the twin as already programmed - refused, not overwritten.

The spans hold still. Every bench write session here ended back on the
baseline's sha256 over the whole image, aux area included: the UV-82 on
2026-08-20, the UV-5G on 2026-08-30 and the UV-5R on 2026-09-05. boofwang never
writes them, because every owned range ends at `0x1808`.

**The check.** After the handshake and before anything is sent, `writeImage`
reads radio `0x0000` and discards it, then reads `0x1F00`, `0x1F40` and
`0x1F80`. Those three are the blocks `_get_aux_data_from_radio` reads, taken in
`0x40` blocks on the boundaries `readImage` uses, because a sixteen-byte read
on the UV-5R can answer with another block's bytes. `0x0000` is there for the
order. The handshake ends on `0x1FC0`, the block some units drop a byte from,
and nothing had ever followed it with an aux read: `readImage` reads `0x0000`
next, an edit sends its first frame, and CHIRP reads `0x1FC0` last. With
`0x0000` first, every step is one `readImage` already takes. The first version
of the check went straight from `0x1FC0` to `0x1F00`, and the adversarial
review caught it. It then refuses:

- a backup that carries no fingerprint;
- a backup of a different unit;
- an image of a different unit - the restore screen hands over the image as its
  own backup, so a restore of another unit's backup is refused at the line
  above;
- a base image of a different unit, which on the diff-driven members would
  leave the radio holding a mixture of two codeplugs;
- an image that stops before the aux block, which cannot be fingerprinted at
  all.

**Backups stored before the fingerprint.** Every one has a null fingerprint,
and the driver refuses a null, as the DM-32UV's does. Nobody has to read their
radio again to get past that, because every backup this family stored is the
whole 6,472-byte read, aux area included. The app computes the fingerprint from
the backup's own bytes before offering it (`chooseBackup` in
`lib/storage/choose-backup.ts`): the same function on the same bytes, at a
later time. A null now reaches the driver only for bytes that cannot be
fingerprinted. `chooseBackup` serves every radio, so a DM-32UV backup stored
before that driver's own check is now fingerprinted from its calibration block
the same way, where it used to be refused. The same change made the app offer
the newest backup *of the unit* rather than the newest with a matching
`identHash`, which on two identical radios could be the other one's.

### What opening a file does to a write

The UV-82 and UV-5G send only the blocks that differ from the image the open
codeplug came from. When that image is a file older than what the radio holds,
the blocks nobody edited keep the radio's own bytes while the screen shows the
file's. The UV-5R sweeps every owned block and does not have the problem.

The fingerprint briefly made this easier to reach. Opening a file of the model
already open asks whether to apply it to the open codeplug instead, and that
question was skipped for any file known to come from the same radio - which,
once this family had a fingerprint, began to include its files. It is skipped
now only when the file holds the open codeplug's own bytes
(`nothingToTransplant` in `lib/radio/transplant.ts`).
Applying keeps the read as the base. Opening a file with nothing open, or a
backup from the backups page, still asks nothing, and the driver does not
compare a base with the radio. That predates the fingerprint and is not fixed
here.

### Not verified

- **No hardware session has sent the four reads.** `test/hardware/uv5g.spec.ts`
  and `test/hardware/uv5r.spec.ts` now do, and send a backup of some other unit
  first to see it refused. Neither has been run since. There is no UV-82 bench
  spec, so on the UV-82 the check has only met a scripted radio.
- **The order on the wire is new as a whole.** The handshake reads `0x1E80`,
  `0x1EC0` and `0x1FC0`, then `0x0000`, then the three. Every step is one
  `readImage` takes, and the rule CHIRP documents - a block outside the aux
  area first - is kept. No radio has been sent the sequence, and the bench
  UV-5R is a unit that drops a byte at `0x1FCF`. If a write session ever finds
  the three disagreeing with what a read stored, the check refuses every write
  and restore on that unit and a fresh read does not cure it, so that is the
  first thing to look at.
- **The span bytes are unexplained.** The claims rest on two pairs of radios
  and seven images, and on the spans not moving across three write sessions.
  They are not a decode.

## Firmware string

The version is `block1[48:62]` of the auxiliary area, and on this unit that
window holds `N822413N822413` - the version stored twice. CHIRP takes the same
fourteen bytes and matches its BASETYPE tables with `startswith`, so the
doubling is harmless. It is left as read rather than trimmed, because the
variant string is what the write gate compares an image against, and changing
how it is derived would make every backup taken before the change look like it
came from a different radio.
